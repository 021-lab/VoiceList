# Задание кодеру: модуль синхронизации VoiceList → taosmd (v1)

Это точка входа ветки `taosmd-backend`. Перед началом прочитать: [INTEGRATION_taosmd.md](./INTEGRATION_taosmd.md) (архитектура доступа) и канон бэкенда: https://github.com/021-lab/TaOS/tree/feat/user-statuses/docs/specs (начать с `00-INDEX-focus-harness.md`; для этой задачи нужны разделы A2A и Archive контракта).

## Архитектура (решение владельца, не пересматривать)

```
Приложение → localStorage → sync-модуль → (Worker-proxy /api) → taosmd
```

- Текущий бэкенд приложения живёт в браузере (localStorage) и там же остаётся: UX и офлайн-работа не меняются.
- Sync-модуль — новый слой внутри того же единственного файла приложения: исходник в `src/`, собирается в self-contained `list-manager.html` через `npm run prepare-preview`. Никаких внешних бандлов/зависимостей.
- Синк в v1 **односторонний** (локал → taosmd) плюс **bootstrap**: на пустом localStorage состояние загружается из taosmd.
- Носитель синка — **журнал действий приложения**: каждая запись лога парсится в A2A-сообщение в выделенный канал лога. В taosmd каждое такое сообщение автоматически становится событием append-only архива — долговременная истина теперь там, localStorage — рабочая реплика.
- Маппинг в граф задач taosmd (`/tasks`) в v1 НЕ делается — это v2.

## Механика v1

1. **Push**: новые записи журнала отправляются по порядку: `POST /api/a2a/send` с `{from: "user", thread: "voicelist-log", body: <JSON операции>}`. Одна запись журнала = одно сообщение. Локально хранится курсор «докуда отправлено».
2. **Формат body**: `{id, ts, op, payload}` — использовать существующий словарь операций журнала приложения как есть, новый не изобретать; `id` операции — стабильный (для дедупа при replay). Фактический словарь op задокументировать в этом файле по итогам чтения кода журнала.
3. **Bootstrap**: если localStorage пуст — `GET /api/a2a/messages?thread=voicelist-log&since=0` (пагинация по `since`), replay операций через существующую логику применения, дубли отбрасываются по `id`. После replay курсор выставляется в конец (повторная отправка восстановленных операций не происходит).
4. **Офлайн/ретраи**: неотправленные записи копятся и догоняют при появлении сети; отправка не блокирует UI; экспоненциальный бэкофф, порядок сохраняется (не слать N+1, пока не подтверждён N).
5. **Конфликтов нет по построению**: единственный писатель канала — этот клиент; двусторонний мердж не реализуется.
6. **Статус синка в UI**: минимальный индикатор (последний успех / ошибка / размер очереди).

## Правила

- `from` всегда `user` — провенанс-конвенция проекта (канон: TASK_LIFECYCLE §4.6).
- Секреты в журнал не писать; сервер дополнительно редактирует своими паттернами.
- Токен taosmd в браузер не попадает никогда — его добавляет Worker-proxy (см. INTEGRATION §1).
- Адрес API — относительный `/api/*` (same-origin); для локальной разработки — конфигурируемый base URL, без хардкода домена (fork-friendly правило репо).
- Если taosmd недоступен — приложение работает как раньше, синк молча копит очередь.

## Приёмка

1. Свежий браузер (пустой localStorage) + непустой канал `voicelist-log` → приложение восстанавливает состояние, эквивалентное исходному.
2. Операции, сделанные офлайн, догоняют канал при появлении сети; перезапуск вкладки не дублирует сообщения (дедуп по id проверяется через повторный bootstrap).
3. Все операции видны в `GET /api/a2a/messages?thread=voicelist-log` с `from=user`, порядок совпадает с журналом.
4. `npm run test:unit` и `npm run test:e2e` зелёные; unit-тесты на курсор/дедуп/бэкофф добавлены.
5. Приложение остаётся self-contained одним файлом; `npm run prepare-preview` собирает; htmlpreview-ссылка работает (синк в этом режиме просто копит очередь).

## Вне скоупа v1

Маппинг в `/tasks` (двусторонний синк с графом задач и статусами focus/pause бэкенда) — v2; агенты, гейты, голосовой ввод через бэкенд.
