# TASK_RESOLVER — поиск задачи по нечёткому голосовому вводу

Статус: draft v1 (2026-07-09). Эталонная реализация `resolve()` из
`VOICE_INTERFACE.md` §1 и формальное пространство параметров для
оптимизации. Пресетов нет: оптимизация идёт по всему вектору параметров
Θ; неизменны только инварианты §3.

Архитектура: есть таблица задач, по которой можно искать; входной текст
**преобразуется** в поисковые паттерны так, чтобы один запрос вернул все
похожие задачи (recall-superset); решение о кандидатах принимается в
коде над найденным множеством. Никаких вспомогательных таблиц и
индексов. Где живёт таблица — деталь исполнения (локальная копия
поллинга `GET /tasks` или upstream-предложение `/tasks/resolve`),
форма запроса одна.

## 1. Контракт

```
resolve(text, Θ) → One(id) | Vector([{id, подпись}...]) | Empty
```

- `One` — уверенное совпадение: команда пишет молча.
- `Vector` — сомнение: оверлей кандидатов (VOICE_INTERFACE §4).
- `Empty` — «не нашёл»: toast + лог, без записей.

Охват: задачи со `status ∉ {closed, superseded}`.

## 2. Параметры Θ — формальное описание

### 2.1 Нормализация (не параметр, фиксирована)

lowercase → `ё→е` → убрать пунктуацию → токенизация по пробелам.
«Купить Смеситель!» → `[купить, смеситель]`. Вход и названия
нормализуются одинаково.

### 2.2 Ярусы совпадения пары токенов

Пара (токен запроса, токен названия) получает силу — наибольший
сработавший ярус:

| Ярус | Вес | Условие | Параметры |
|---|---|---|---|
| точный | `W_EXACT` | токены равны | `W_EXACT = 3` |
| стем | `W_STEM` | общий префикс ≥ `STEM_PREFIX` символов **и** ≥ `STEM_NUM/STEM_DEN` длины короткого токена | `W_STEM = 2`, `STEM_PREFIX = 4`, `STEM_NUM/STEM_DEN = 2/3` |
| опечатка | `W_TYPO` | расстояние Дамерау–Левенштейна ≤ `TYPO_DIST` при длине обоих ≥ `TYPO_MINLEN` | `W_TYPO = 1`, `TYPO_DIST = 1`, `TYPO_MINLEN = 5` |

Ограничение на веса: `W_EXACT > W_STEM > W_TYPO > 0`, все целые.

Примеры:
- «ванную» × «ванная»: общий префикс `ванн` = 4 ≥ STEM_PREFIX,
  4 ≥ ⌈2/3·6⌉ = 4 → **стем**. Русская морфология из ASR снимается без
  словарей.
- «сместитель» × «смеситель»: DL-расстояние 1, длины ≥ 5 → **опечатка**.
- «свет» × «света»: префикс 4, но 4 ≥ ⌈2/3·4⌉ = 3 → стем. А «сон» ×
  «сони»: префикс 3 < STEM_PREFIX → нет (короткие слова стемом не
  склеиваются — защита от ложных склеек).
- `TYPO_DIST = 0` полностью выключает ярус опечаток.

### 2.3 Подпись кандидата

Кортеж целых `(m, s, t)`:
- `m` — сколько токенов запроса нашли пару (каждый — по лучшему ярусу,
  жадно без повторного использования токенов названия);
- `s` — сумма весов этих пар;
- `t` — сколько токенов названия покрыто.

Сравнение кандидатов — лексикографическое по `(m, s, t)`.

Пример: запрос `[купить, смеситель]`, название «Купить смеситель» →
(2, 6, 2); название «Установить смеситель» → (1, 3, 1).

### 2.4 Параметры решения

| Параметр | Дефолт | Смысл | Пример подкрутки |
|---|---|---|---|
| `MAX_MISS` | 0 | правило R2: сколько токенов запроса может не найтись при уверенном полном покрытии | `MAX_MISS=1`: «большой синий шкаф» уверенно найдёт «Синий шкаф» |
| `COVER_NUM/COVER_DEN` | 1/2 | правило R3: минимальная доля найденных токенов запроса | `2/3` строже: из трёх слов должны совпасть два |
| `LEAD` | 1 | правило R3: отрыв лучшего от второго в **целых токенах** `m` | `LEAD=2`: молчаливая запись только при отрыве в два слова |
| `CAND_LIMIT` | 7 | максимум кандидатов в оверлее | — |

Монотонность (проверяемое свойство для оптимизатора): ужесточение
любого параметра (`TYPO_DIST↓`, `STEM_PREFIX↑`, `COVER↑`, `LEAD↑`,
`MAX_MISS↓`, `W_*` при сохранении порядка) может только **сужать**
множество молчаливых записей. Property-тест: `silent(Θ_строже) ⊆
silent(Θ_мягче)` на корпусе запросов.

Вектор Θ может задаваться отдельно на класс глагола (деструктивные
`удали`/`вместо`/`после` — строже; навигационные `открой` — мягче) —
это ещё одно измерение оптимизации, инварианты §3 общие для всех.

## 3. Инварианты вне Θ (пол, не подкручивается)

1. Точное нормализованное равенство запроса и названия ровно одной
   задачи → всегда `One`.
2. Ничья лучших по подписи `(m, s)` — всегда `Vector`, ничья **никогда**
   не разрешается молча (ни рекентностью, ни видимостью, ни
   приоритетом; они сортируют кандидатов внутри оверлея, но не выбирают
   за пользователя).
3. `m_max = 0` → всегда `Empty`.

## 4. Псевдокод — преобразование запроса + один SELECT

### 4.1 Преобразование текста в паттерны

Для каждого токена запроса `q` (после нормализации §2.1):

| Паттерн | Когда | Что гарантированно ловит |
|---|---|---|
| `q[:STEM_PREFIX]` (первые 4 символа) | len(q) ≥ 4 | **точный** ярус (название содержит q целиком, значит и его префикс) и **стем** (стем по определению — общий префикс ≥ 4) |
| три части `q` (≈ по трети) | len(q) ≥ TYPO_MINLEN | **опечатку** DL ≤ 1: одиночная правка локальна и задевает максимум две соседние части — хотя бы одна треть остаётся в названии нетронутой (включая транспозицию на границе частей) |
| `q` целиком | len(q) < 4 | короткие слова — только точный ярус (стему нужен префикс ≥ 4, опечатке — длина ≥ 5) |

Пример: «сместитель» → `['смес', 'смес', 'тите', 'ль']` → отбрасываем
куски короче 2 → паттерны `{смес, тите, ль→нет}`; название «Купить
смеситель» ловится и по `смес`, и по хвостовой части.

Это фильтр **полноты**, не точности: паттерн `смес%` соберёт и «смесь»,
и «смеситель» — точность добирается ярусами §2.2 над найденным
множеством. Ложных пропусков нет по построению.

### 4.2 Один запрос

```sql
SELECT id, title, title_norm, status
FROM tasks
WHERE status NOT IN ('closed','superseded')
  AND ( title_norm LIKE '%' || :p1 || '%'
     OR title_norm LIKE '%' || :p2 || '%'
     OR ... )                       -- дизъюнкция всех паттернов всех токенов
LIMIT :FOUND_CAP;                   -- страховка, дефолт 200 + предупреждение в лог
```

Таблица задач мала (сотни строк), скан по ней тривиален; память
ограничена размером найденного множества и `FOUND_CAP`.

### 4.3 Решение над найденным множеством (в коде)

```
resolve(text, Θ):
  Q = tokenize(normalize(text)); rows = SELECT выше

  R1: title_norm = norm(text) ровно у одной строки → One;
      у нескольких → Vector (дубли имён)

  for row in rows:                       # малое множество
    for q ∈ Q × токены названия:
      ярус по §2.2: точный / стем (доля префикса) / DL ≤ TYPO_DIST
    подпись (m, s, t) — жадное паросочетание, §2.3

  строки с m = 0 отбрасываются           # паттерн зацепил, ярусы — нет
  if пусто: return Empty                 # инвариант 3
  сортировка по (m, s, t); best, second
  R2 / R3 по параметрам Θ (§2.4); ничья по (m, s) → Vector  # инвариант 2
  return One(best) | Vector(top CAND_LIMIT)
```

Разделение ответственности: паттерны отвечают за то, чтобы **ни один
настоящий кандидат не потерялся** (recall), ярусы и подписи — за то,
чтобы **лишние отвалились** (precision), правила R1–R3 — за выбор между
молчаливой записью, оверлеем и «не нашёл».

## 4.4 Рабочая реализация

`resolver.js` — эталонный код §§2–4: параметры Θ вынесены в константы в
шапке файла, экспортируются `queryPatterns` / `buildQuery` (SQL-путь) /
`findCandidates` (отбор по массиву поллинга) / `resolve` /
`resolveOverTasks`. `test_resolver.js` прогоняет корпус §5; оба файла
кладутся в репо как есть (юнит-job CI запускает `node test_resolver.js`).

В этом репозитории оба файла лежат в `src/`; команда CI —
`node src/test_resolver.js`.
