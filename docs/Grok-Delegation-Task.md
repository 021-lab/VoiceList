# Задача: делегирование задачи Грок-боту

Репозиторий `021-lab/VoiceList`, база — ветка `Claude/live-button`. Работать по правилам
репозитория (`AGENTS.md`, `docs/DECISIONS.md`): своя ветка от базовой, одна правка — один
коммит, подписи коммитов — словами пользователя.

## Что нужно

1. На карточке задачи (`#task-page`) — блок «Грок»: тред делегирования, поле ввода и кнопка
   «Делегировать Гроку».
2. Отправка уходит из Worker'а на вебхук рутины Грок-бота. Бот отвечает POST-запросом на наш
   Worker, ответ ложится в тот же тред.
3. Во фронтире под делегированной задачей — блок с последним сообщением Грока.
4. Грок не меняет дерево. Единственное исключение — флаг `done` в ответе: задача переходит в
   Done обычной командой графа.
5. Кнопка «Открыть в Гроке» — глубокая ссылка в чат бота с подставленной задачей.
6. Инструмент для бота: публикация HTML-страницы на Cloudflare, в ответ — ссылка, которую бот
   кладёт в свой ответ как результат работы.

## Секреты Worker'а

Задаёт владелец; в коде и в логах не появляются.

| Секрет | Что это |
|---|---|
| `GROK_WEBHOOK_URL` | Адрес «POST to» из вебхука рутины Грок-бота |
| `GROK_WEBHOOK_KEY` | Ключ из того же вебхука, уходит как `Authorization: Bearer <key>` |
| `GROK_REPLY_TOKEN` | Наш токен, которым Грок подписывает ответы, чтение треда и публикацию страниц |

Не секрет, переменная: `GROK_BOT_ID` — id бота для глубокой ссылки (конец ссылки из Share →
Copy link). Пусто — ссылка открывает основного бота.

Если секретов нет — блок на карточке показывает «Грок не подключён», кнопка неактивна.

## Хранение

Отдельная таблица в SQLite Durable Object (рядом с `vl_*`), не в снимке документа:

```
grok_messages(
  id TEXT PRIMARY KEY,   -- id сообщения; для ответов Грока = replyId
  task_id TEXT NOT NULL,
  role TEXT NOT NULL,    -- user | grok | system
  text TEXT NOT NULL,
  at TEXT NOT NULL,      -- ISO
  reply_to TEXT,         -- для ответов Грока: id сообщения пользователя
  run_uuid TEXT,         -- runUuid из ответа вебхука
  state TEXT             -- для user: sending | accepted | failed
)
```

Тред задачи — все строки с её `task_id` по времени. Удаление и архивирование задачи тред не
трогают.

## Исходящий запрос: POST /api/grok/delegate

Тело от клиента: `{ "taskId": "...", "messageId": "<uuid клиента>", "text": "..." }`.
`messageId` делает повтор идемпотентным: повторная отправка того же id не создаёт второе
сообщение и не будит бота второй раз, если первый вызов уже принят.

Worker:
1. Проверяет задачу, сохраняет сообщение `role=user, state=sending`, рассылает обновление.
2. Шлёт POST на `GROK_WEBHOOK_URL` с `Authorization: Bearer GROK_WEBHOOK_KEY` и телом:

```json
{
  "kind": "voicelist.delegation",
  "taskId": "t42",
  "message": { "id": "m-uuid", "text": "Найди три варианта …", "at": "2026-11-24T10:00:00Z" },
  "task": {
    "title": "Купить кондиционер",
    "status": "Open",
    "deadline": null,
    "path": ["Дом", "Спальня"],
    "children": [{ "title": "Замерить комнату", "status": "Done" }]
  },
  "thread": [
    { "id": "m-prev", "role": "user", "text": "…", "at": "…" },
    { "id": "r-prev", "role": "grok", "text": "…", "at": "…" }
  ],
  "reply": { "url": "https://<хост этого Worker'а>/api/grok/reply" }
}
```

`thread` — прежние сообщения треда без текущего, последние 30, без `system`. `reply.url`
строится из хоста запроса, чтобы дев и прод отвечали каждый себе.

3. Разбор ответа вебхука (он синхронный и подтверждает только запуск, не выполнение):
   - `200 {"success":true,"runUuid":"…"}` → `state=accepted`, сохранить `run_uuid`.
   - `401` → `failed`, системное сообщение «Ключ вебхука неверный или перевыпущен».
   - `400` → `failed`, «Рутина Грока выключена или упёрлась в лимит запусков».
   - `404` → `failed`, «Вебхук Грока больше не существует».
   - `5xx` / сеть / таймаут 15 с → `failed`, «Грок не ответил на вызов».
   Автоповторов нет: у сообщения в состоянии `failed` кнопка «Повторить» (тот же `messageId`).

Если в настройках вебхука вместо Bearer-ключа выдан signing secret `whsec_…`, подписывать
запрос по Standard Webhooks (`webhook-id`, `webhook-timestamp`, `webhook-signature` =
`v1,` + base64 HMAC-SHA256 от `{id}.{timestamp}.{body}`). Поддержать оба варианта по
префиксу ключа.

## Входящий ответ: POST /api/grok/reply

Заголовок `Authorization: Bearer GROK_REPLY_TOKEN`, сравнение за постоянное время. Origin у
бота нет — существующая проверка Origin его не задевает, CORS не нужен. Тело до 32 КБ
(`readBoundedJson`):

```json
{
  "taskId": "t42",
  "replyTo": "m-uuid",
  "replyId": "r-uuid",
  "text": "Нашёл три варианта: …",
  "done": false
}
```

- `text` обязателен, до 8000 символов; `done` необязателен.
- `replyTo` необязателен: бот может написать в тред и по разговору в своём приложении, без
  вызова вебхука.
- `401` — токен неверный; `404` — нет такой задачи; `400` — тело некорректно.
- Повтор с уже записанным `replyId` → `200 {"stored":true,"duplicate":true}`, без второй
  записи и без второго `done`.
- Успех → `200 {"stored":true}`: строка `role=grok`, рассылка обновления открытым вкладкам.
- `done: true` → тот же путь команд графа, что у остальных источников: `setStatus Done` с
  `source: "grok"`. Попадает в журнал и откатывается как любое действие. Если задача уже
  Done или Archive — статус не трогать.

## Чтение треда: GET /api/grok/thread?taskId=…

Тот же `Authorization: Bearer GROK_REPLY_TOKEN`. Отдаёт то же, что уходит в вебхук, без
`message`: `{ taskId, task, thread, reply }`. Нужен боту, когда разговор продолжают в его
приложении по глубокой ссылке и вебхука с контекстом не было.

## Публикация страниц: инструмент для бота

Бот публикует готовую HTML-страницу и получает ссылку, которую отдаёт как результат работы.

Хранение — R2, новый бакет и биндинг `GROK_PAGES` (отдельные бакеты для дева и прода).
Метаданные страницы — в той же SQLite: `grok_pages(id, task_id, title, size, created_at,
updated_at)`.

Отдача — **на отдельном домене**, не на домене приложения: `vlist-pages.smileme.ai` для прода
(для дева — свой). Тот же Worker, маршрутизация по `Host`: на домене страниц отвечает только
`GET /p/<id>`, всё остальное — 404. Иначе скрипт страницы исполнится на origin приложения и
пройдёт проверку Origin у `/api/*`.

Заголовки ответа страницы:
- `Content-Type: text/html; charset=utf-8`
- `Content-Security-Policy: sandbox allow-scripts allow-popups allow-forms allow-modals`
  (без `allow-same-origin`) — вторая линия изоляции;
- `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`.

API (на домене приложения, `Authorization: Bearer GROK_REPLY_TOKEN`):

| Запрос | Что делает |
|---|---|
| `POST /api/grok/pages?taskId=…&title=…` | Тело — сырой HTML (`Content-Type: text/html`), до 10 МБ. Ответ `201 { id, url }` |
| `PUT /api/grok/pages/<id>` | Заменяет содержимое той же страницы, ссылка не меняется. `200 { id, url }` |
| `DELETE /api/grok/pages/<id>` | Удаляет страницу. `204` |

- `id` — 128 бит случайности (base32/base64url): ссылка — единственный доступ к странице,
  угадываться не должна.
- `taskId` необязателен; если задан — проверяется, страница привязывается к задаче.
- `url` — полный адрес на домене страниц: `https://vlist-pages.smileme.ai/p/<id>`.
- `413` — больше 10 МБ; `401` — токен; `404` — нет задачи или страницы.
- Публикация, замена и удаление логируются (id, задача, размер, sha256 тела).

В интерфейсе: ссылки на домен страниц в треде и во фронтире — обычные кликабельные ссылки,
открываются в новой вкладке. На карточке задачи под тредом — список страниц задачи
(заголовок, время, ссылка).

## Интерфейс

Карточка задачи, блок «Грок» под подзадачами:
- Тред: сообщения пользователя и Грока с временем; системные — мелким серым.
- Текст Грока — plain text с переносами строк и кликабельными ссылками; HTML не рендерить.
- Под последним принятым сообщением пользователя, пока нет ответа, — «Грок работает…».
- Поле ввода и кнопка «Делегировать Гроку». Пустой текст не отправляется; во время
  отправки кнопка неактивна.
- Повторные сообщения идут в тот же тред тем же полем и кнопкой.
- Кнопка «Открыть в Гроке» — глубокая ссылка в чат бота:
  `grokbot://app/v1/prompt?id=<GROK_BOT_ID>&text=<urlencode(текст)>`, без `id`, если
  `GROK_BOT_ID` пуст. Текст: `VoiceList, задача <taskId> «<title>». ` — до 1000 символов
  после кодирования, название обрезать. Бот по нему сам читает тред через
  `/api/grok/thread`. Ссылка работает только при установленном и залогиненном приложении
  Grok Bot; текст лишь подставляется в пустое поле, отправляет пользователь.

Фронтир, под задачей с непустым тредом:
- Последнее сообщение Грока — две строки с обрезкой и время.
- Если последнее слово за пользователем — «Грок работает…»; если вызов упал — текст ошибки.
- Тап по блоку открывает карточку задачи на блоке «Грок».

Обновления в открытые вкладки — тем же каналом, что и снимок документа; без поллинга.

## Логирование

По инварианту проекта: исходящее тело вебхука и сырой входящий ответ логируются рядом с
сообщением, с кодом ответа вебхука и `runUuid`. Ключи и токен в лог не попадают.

## Тесты

- Юнит: `/api/grok/delegate` с замоканным вебхуком — все коды ответа, идемпотентность по
  `messageId`.
- Юнит: `/api/grok/reply` — неверный токен, нет задачи, дубль `replyId`, `done` на открытой
  и на закрытой задаче, откат `done`.
- Юнит: `/api/grok/thread` — токен, нет задачи.
- Юнит: страницы — публикация, замена с той же ссылкой, удаление, 413, 401; на домене страниц
  отвечает только `/p/<id>`, на домене приложения `/p/<id>` — 404; заголовок CSP sandbox на
  месте.
- Юнит: глубокая ссылка — кодирование, обрезка до 1000 символов, без `id` при пустом
  `GROK_BOT_ID`.
- e2e (Playwright): отправка с карточки, появление ответа в треде и во фронтире без
  перезагрузки, тап по блоку фронтира открывает карточку.
