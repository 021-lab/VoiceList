# INPUT_HANDLING_STANDARD

Стандарт приёма пользовательского ввода для подключаемого модуля списка.

Стандарт не привязан к репозиторию, фреймворку и бэкенду: любое
приложение, встраивающее модуль списка, обязано соблюдать §2–§6, и любая
реализация, соблюдающая их, считается совместимой.

Смежные документы:

| Документ | Что определяет |
|---|---|
| `COMMAND_RESOLVER.md` | Разбор фразы на глагол и остаток, таблица фреймов, Θ команд |
| `TASK_RESOLVER.md` | Сопоставление остатка с задачей, параметры Θ целей. Реализация — `resolver.js` |
| `PROPOSAL_voice-input.md` | Привязка к конкретному репозиторию: адаптеры, имена полей, порядок работ |

---

## 1. Концепция

Модуль списка — самодостаточный компонент, который PWA-приложение
подключает к себе, чтобы получить иерархический список и голосовое
управление им. Приложение отвечает за данные и за домен; модуль отвечает
за то, как пользователь выражает намерение и как это намерение
превращается в команду.

Поток однонаправленный, три слоя:

```
жест + речь  →  ПРИЁМ ВВОДА  →  РАСПОЗНАВАТЕЛЬ  →  ИСПОЛНИТЕЛЬ  →  патч
                  (§3–§4)         (§5)              (§6)
```

Приём ввода не знает бизнес-логики. Распознаватель не изменяет состояние.
Исполнитель не разбирает текст. Слои не перепрыгиваются.

Функции с похожими ролями — не путать:

| Имя | Что делает | Где определён |
|---|---|---|
| `resolveCommands(text, context, snapshot)` | текст → кандидаты-команды | §5 |
| `parseCommand(text, context)` | текст → гипотезы команд | `COMMAND_RESOLVER.md` |
| `resolver.resolve(text, rows)` | текст → `One \| Vector \| Empty` | `TASK_RESOLVER.md` |
| `execute(state, command)` | команда → патч | §6 |

`resolveCommands` вызывает `parseCommand`, а для команд с целью передаёт
остаток в `resolver.resolve`. Обратных зависимостей нет.

### Принципы

1. **Один жест — носитель всего голосового управления.** Отдельных кнопок
   записи, режимов и модальностей помимо §3 не существует.
2. **Подтверждение до исполнения, а не отмена после.** Пользователь видит
   команду, которая будет выполнена, прежде чем отпустить палец.
   Единственное исключение — фолбэк на модель (§8).
3. **Речь и текст неразличимы ниже слоя приёма.** Транскрипт и строка с
   клавиатуры проходят одну грамматику и один путь.
4. **Всё, что доступно пользователю, доступно тестирующему агенту** через
   тот же контракт, без отдельной ветки логики (§10).
5. **Модуль не владеет данными.** Он получает снимок и отдаёт патч.
6. **Проблема показывается, а не проглатывается.** Любой отказ — доступа,
   распознавания, канала — оканчивается сообщением пользователю и записью
   в журнал. Молчаливого «ничего не произошло» быть не должно.

## 2. Границы с приложением-хостом

### Что предоставляет модуль

- Разметку и монтирование интерактивных элементов списка.
- Обработку жестов и полноэкранный оверлей (§3–§4).
- Распознаватель и базовый словарь команд (§5, §7).
- Формат записи журнала действий (§9).
- Тестовый хук (§10).

### Что обязан предоставить хост

| Ресурс | Требование |
|---|---|
| Снимок списка | Плоский массив элементов, каждый с полями по таблице ниже |
| Адаптер снимка | Приведение полей хоста к тому, что ждёт резолвер цели: `{id, title, status}`. `resolver.js` не переписывается под хост — адаптируется вход |
| Исполнитель | Реализация контракта §6, покрывающая обязательный минимум команд |
| ASR-адаптер | Контракт ниже |
| Фолбэк-канал | Точка, принимающая сырой транскрипт и возвращающая команду (§8) |
| Персистентность | Куда уходит патч после исполнения — дело хоста; модуль этого не видит |

Обязательные поля элемента снимка:

| Смысл | Обязательность |
|---|---|
| Идентификатор | Обязательно, уникален |
| Родитель | Обязательно, `null` для корня |
| Порядок среди соседей | Обязательно |
| Статус | Обязательно |
| Отображаемый текст | Обязательно — по нему работает резолвер цели |

Имена полей задаёт хост и объявляет в адаптере снимка. Модуль не
предполагает конкретных имён.

### Контракт ASR-адаптера

Адаптер отдаёт три вида событий: промежуточный транскрипт, финальный
транскрипт, ошибка. Модуль не знает, чем адаптер реализован.

| Ситуация | Поведение | Сообщение |
|---|---|---|
| Отказ в доступе к микрофону | Оверлей не взводится, жест не начинается | «Нет доступа к микрофону» с подсказкой, где его включить |
| Обрыв распознавания в середине жеста | Оверлей закрывается, команда не исполняется | «Распознавание прервано» |
| Финальный транскрипт не пришёл за `FINAL_TIMEOUT_MS` после отпускания | Команда не исполняется — исполнять промежуточный запрещено (§11) | «Не расслышал, повторите» |
| Адаптер не отдаёт промежуточных результатов | Деградированный режим, см. ниже | Пометка в оверлее при взводе |

**Деградированный режим.** Без промежуточного транскрипта стек кандидатов
пуст всё время удержания, и выбирать не из чего. В этом случае оверлей
показывает только «как есть» и отмену, а при взводе сообщает, что выбор
команды недоступен. Речь целиком уходит в фолбэк на модель. Режим
включается по факту отсутствия промежуточных событий, а не настройкой.

Каждый из этих случаев пишется в журнал как событие без патча.

### Актуальность снимка

Снимок — копия. Источник данных за время жеста может измениться: другое
устройство, агент, отложенная синхронизация. Между моментом, когда
резолвер выбрал цель, и моментом коммита цель может исчезнуть или
переехать.

Правило: **перед исполнением команда проверяется на существование всех
своих идентификаторов в текущем снимке.** Если хотя бы один отсутствует —
команда не исполняется, показывается сообщение, событие пишется в журнал.
Модуль не пытается угадать замену и не разрешает конфликт содержательно:
согласование снимка с источником и разрешение конкурирующих записей —
обязанность хоста.

### Чего модуль не делает никогда

- Не решает, где хранятся данные, и не обращается к хранилищу напрямую.
- Не выполняет сетевых запросов иначе как через фолбэк-канал хоста.
- Не рендерит доменные экраны приложения — только сообщает хосту, что их
  следует открыть, через `effect` (§6).
- Не хранит состояние между жестами, кроме параметров конфигурации.

### Точки расширения

Хост может добавить свои команды в словарь, переопределить действие тапа
для конкретного `agent-action-id` и переопределить любую константу §3.
Остальное менять нельзя, иначе теряется совместимость.

Переопределения тапа задаются **единой таблицей** `elementId → действие` в
одном месте. Разбрасывать их по коду рендера запрещено (§11).

### Маркировка элементов

Каждый интерактивный элемент обязан нести атрибут `agent-action-id` с
уникальным в пределах страницы значением: идентификатор элемента списка,
идентификатор строки журнала или фиксированное имя кнопки. Элемент,
доступный пользователю, но не помеченный, — нарушение стандарта.

## 3. Жесты

Распознаются три жеста. Остальные (мультитач, свайп вправо, удержание вне
списка без речи) игнорируются молча.

| Жест | Условие | Результат |
|---|---|---|
| **Тап** | Касание короче `LONGPRESS_MS`, смещение меньше `ARM_SLOP_PX` | Действие элемента по таблице переопределений; по умолчанию — открыть поле ввода с кнопкой «Отправить» |
| **Удержание** | Касание в любой точке экрана дольше `LONGPRESS_MS` при смещении меньше `ARM_SLOP_PX` | Оверлей **без контекста** |
| **Свайп влево по элементу** | Начато на элементе списка; горизонтальное смещение достигло `CONTEXT_DX_PX` при `\|dx\| > CONTEXT_RATIO · \|dy\|` в пределах `CONTEXT_WINDOW_MS` от начала касания | Оверлей **с контекстом**; контекст — элемент, на котором был палец |

### Приоритет прокрутки

До взвода оверлея прокрутка выигрывает всегда. Вертикальное смещение
больше `ARM_SLOP_PX` до истечения `LONGPRESS_MS` отменяет жест целиком и
отдаёт движение скроллу. Слушатели регистрируются как `passive` вплоть до
момента взвода. После взвода прокрутка блокируется, и всё движение пальца
интерпретируется как выбор в оверлее.

Свайп влево — исключение: взводит оверлей немедленно, не дожидаясь
таймера. Проверка соотношения отсекает диагональное движение, поэтому
обычная прокрутка его не запускает.

### Краевые случаи

1. Горизонтальное движение **после** взвода игнорируется. Контекст
   фиксируется один раз, в момент взвода, и в течение жеста не меняется.
2. Удержание на элементе списка даёт оверлей **без** контекста. Контекст
   даёт только свайп влево.
3. Микрофон включается в момент взвода оверлея, не раньше. Речь до взвода
   не захватывается.
4. Второе касание во время жеста игнорируется; жест ведёт первый палец.
5. Прерывание системой (звонок, сворачивание, потеря фокуса) —
   равносильно отмене.
6. Пустой транскрипт при отпускании вне зоны отмены — равносильно отмене.

### Константы

| Константа | Значение | Смысл |
|---|---|---|
| `LONGPRESS_MS` | 400 | Удержание до взвода оверлея |
| `ARM_SLOP_PX` | 10 | Допуск на дрожание пальца до взвода |
| `CONTEXT_DX_PX` | −40 | Порог горизонтального сдвига для контекста |
| `CONTEXT_RATIO` | 2 | Отношение горизонтали к вертикали для отсечки прокрутки |
| `CONTEXT_WINDOW_MS` | 250 | Окно от начала касания, в котором свайп засчитывается |
| `DEADZONE_PX` | 16 | Мёртвая зона вокруг точки пальца |
| `ROW_H_PX` | 48 | Высота строки кандидата |
| `CANCEL_ZONE_PX` | 56 | Отступ вниз до зоны отмены |
| `FREEZE_DY_PX` | 24 | Сдвиг вверх, после которого порядок кандидатов замораживается |
| `MIN_HOLD_MS` | 150 | Отпускание раньше при пустом транскрипте — отмена |
| `FINAL_TIMEOUT_MS` | 1500 | Ожидание финального транскрипта после отпускания |

## 4. Оверлей

Оверлей занимает весь экран. Вне его интерактивных элементов нет.

### Зоны, сверху вниз

1. **Транскрипция** — у верхней границы, обновляется в реальном времени.
2. **Чип контекста** — под транскрипцией, только в контекстном режиме;
   показывает элемент, к которому будет применена команда. Пользователь
   обязан видеть его до отпускания.
3. **Стек кандидатов** — вверх от пальца, ближайший наиболее вероятен.
   Высота строки `ROW_H_PX`, длина стека не больше `CAND_LIMIT` из
   `resolver.js`.
4. **Точка пальца** — «как есть»: отпускание без смещения отправляет сырой
   транскрипт (§8). Мёртвая зона `DEADZONE_PX`.
5. **Зона отмены** — ниже точки пальца дальше `CANCEL_ZONE_PX`.

### Выбор строки по смещению

`dy` — смещение пальца от точки взвода, вверх положительно:

| Условие | Что выбрано |
|---|---|
| `dy ≤ −CANCEL_ZONE_PX` | Отмена |
| `−CANCEL_ZONE_PX < dy < DEADZONE_PX` | «Как есть» |
| `dy ≥ DEADZONE_PX` | Кандидат с индексом `min(⌊(dy − DEADZONE_PX) / ROW_H_PX⌋, N−1)`, `N` — длина стека |

Если стек пуст, зона кандидатов не существует: любое `dy ≥ DEADZONE_PX`
равносильно «как есть».

Если места вверх не хватает, стек прижимается к нижней границе зоны
транскрипции и прокручивается; зоны 4 и 5 не смещаются, формула
применяется к прокрученному стеку.

### Правила поведения

- **Пересчёт по каждому распознанному слову.** Кандидаты пересчитываются,
  когда в промежуточном транскрипте появляется новое слово — то есть
  когда число токенов выросло. Уточнение последнего слова без роста числа
  токенов пересчёт не запускает. Плюс один пересчёт на финальном
  транскрипте. На каждое событие движка пересчёт не идёт.
- **Заморозка.** Как только палец сместился вверх на `FREEZE_DY_PX`,
  порядок кандидатов фиксируется. Пересчёт продолжается, но строка под
  пальцем не подменяется — иначе пользователь выберет не то, что видел.
- **Коммит по финальному транскрипту.** Отпускание не исполняет команду на
  промежуточном результате: модуль дожидается финала, удерживая выбранную
  позицию, оверлей остаётся на экране с индикатором. Ожидание ограничено
  `FINAL_TIMEOUT_MS` (§2).
- **Стабильность идентификаторов.** Кандидат сохраняет идентификатор между
  пересчётами, иначе заморозка неосуществима.

### Специализация стека

| Намерение | Точка пальца | Стек вверх |
|---|---|---|
| Поиск | Показать найденное | Уточняющие кандидаты запроса |
| Добавление | Добавить с распознанным текстом | Найденные дубли; выбор дубля отменяет добавление и открывает существующий элемент |
| Команда с целью | Наиболее вероятная цель | Остальные кандидаты цели |

Единое правило: **вверх идут кандидаты разрешения цели**, а не смесь
команд и сущностей. Команда однозначна по построению грамматики
(`COMMAND_RESOLVER.md` §5), поэтому выбирать команду в стеке не
приходится — стек всегда однороден.

## 5. Контракт распознавателя

Чистая функция от текста, контекста и снимка. Состояние не меняет, в сеть
не ходит.

```
resolveCommands(text, context, snapshot) → Candidate[]
```

- `text` — транскрипт (промежуточный или финальный) либо строка из поля
  ввода.
- `context` — идентификатор элемента или `null`.
- `snapshot` — актуальный снимок списка от хоста.

| Поле кандидата | Назначение |
|---|---|
| `id` | Стабилен между пересчётами |
| `kind` | `command` или `entity` |
| `label` | Что видит пользователь |
| `hint` | Вторая строка: путь, статус, родитель |
| `score` | Ранг, определяет порядок в стеке |
| `command` | Готовая к исполнению команда по §6, либо `null`, если слот не заполнен |

Кандидат с `command = null` отображается, но не исполняется: отпускание на
нём равносильно отмене.

### Три исхода отпускания

| Где отпущен палец | Что происходит |
|---|---|
| В мёртвой зоне | Сырой транскрипт уходит в фолбэк (§8) |
| На кандидате | `candidate.command` уходит исполнителю |
| В зоне отмены | Только запись в журнал |

## 6. Контракт исполнителя

```
execute(state, command) → { patch, actionLogEntry, viewMode?, effect? }
```

Команда — объект `{ command, actId, payload }`, где `actId` — цель:
идентификатор элемента, к которому команда применяется, или `null` для
команд над списком целиком.

Команды делятся на два класса:

- **Команды изменения** меняют данные. Возвращают патч и запись журнала.
  Отменяемы через `undo`.
- **Команды отображения** данные не трогают. Меняют только то, что
  показано на экране: какой вид открыт, какой элемент раскрыт, какая
  выборка выведена. Возвращают `viewMode` или `effect`, патч пустой,
  **запись журнала не создаётся** — отменять нечего, пользователь просто
  переключает экран.

Класс опознаётся по имени: команда отображения начинается с `show` либо
равна `viewItem`. Это машинная проверка в исполнителе, а не соглашение —
поэтому команда поиска называется `showSearch`.

### Обязательный минимум

| Команда | Класс | Смысл |
|---|---|---|
| `addItem` | изменение | Новый элемент верхнего уровня |
| `addChild` | изменение | Новый ребёнок элемента `actId` |
| `editItem` | изменение | Правка текста |
| `setParent` | изменение | Смена родителя элемента `actId` |
| `setStatus` | изменение | Смена статуса |
| `setTags` | изменение | Переключение тега |
| `toggleCollapse` | изменение | Сворачивание поддерева |
| `deleteItem` | изменение | Удаление вместе с поддеревом |
| `reorderItems` | изменение | Изменение порядка |
| `undo` | изменение | Откат по снимку из `payload` |
| `showSearch` | отображение | Показать выборку по запросу |
| `showList`, `showFrontier`, `showActionLog` | отображение | Переключение вида |
| `viewItem`, `show*Modal` | отображение | Открытие доменного экрана хоста |

**Защита от циклов.** `setParent` обязан отвергать перенос элемента в
самого себя и в любого своего потомка — без патча и без записи журнала.
Распознаватель обязан не показывать такие цели в стеке кандидатов.
Проверка идёт по обходу поддерева переносимого элемента.

## 7. Команды

Формы, разбор и разрешение коллизий — `COMMAND_RESOLVER.md`. Здесь только
то, что относится к интерфейсу.

**Inbox** — служебный элемент верхнего уровня с фиксированным
идентификатором, куда попадает всё, сказанное без контекста. Создаётся при
инициализации, если отсутствует. Не удаляется, не переносится, не
переименовывается: команды `deleteItem`, `setParent` и `editItem` с
`actId` = inbox отвергаются исполнителем.

**Контекст меняет смысл глагола.** «Добавь …» без контекста кладёт в
inbox, с контекстом — создаёт подзадачу. Поэтому чип контекста обязателен:
без него пользователь не отличит два исхода до отпускания.

**Команды с целью.** Остаток фразы передаётся в `resolver.resolve`:

| Исход | Что показывает оверлей |
|---|---|
| `One` | Единственный кандидат у пальца, стек пуст |
| `Vector` | Кандидаты в стеке в порядке убывания ранга |
| `Empty` | Стек пуст, точка пальца — «не найдено», исполнение невозможно |

Приведение снимка к форме `rows` — задача адаптера снимка (§2).

**Два слота.** «Перенеси в …» требует и контекст, и цель. Контекст даёт
свайп, цель даёт стек. Если цель не выбрана — отпускание равносильно
отмене. Команда с незаполненным слотом никогда не исполняется частично.

## 8. Фолбэк на модель

Отпускание в мёртвой зоне отправляет сырой транскрипт через фолбэк-канал
хоста. Сервер возвращает готовую команду, которая исполняется тем же
исполнителем, что и локально распознанные.

- Путь не требует синхронизации с бэкендом данных: команда возвращается на
  фронт и применяется к локальному состоянию.
- **Оптимистичного применения нет.** Модуль не знает, какую команду вернёт
  модель, поэтому применить её заранее невозможно. Оверлей закрывается
  сразу, показывается индикатор ожидания, список меняется по ответу.
- Когда модель определила команду, показывается тост.
- Результат попадает в журнал и отменяется оттуда наравне с остальными.
  Это единственное место, где отмена происходит **после** исполнения.
- **Канал недоступен** (нет сети, ошибка, таймаут): сырой транскрипт
  создаётся как новый элемент в inbox, запись журнала помечается как
  нераспознанная, показывается сообщение. Речь не теряется, действие
  отменяется одним `undo`. Копить очередь и применять её позже нельзя.

---

## 9. Журнал и отмена

Каждая команда изменения создаёт запись: идентификатор, время, исходная
команда, патч, человекочитаемая подпись, статус синхронизации. Команды
отображения записей не создают.

Показ оверлея, отмена, отклонённая команда и любой отказ из §2 фиксируются
как события журнала без патча — это делает разбор промахов распознавания
возможным постфактум.

Отмена выполняется командой `undo`: в `payload` кладётся снимок,
сохранённый до применения отменяемой записи. Хранение снимков —
обязанность журнала.

## 10. Тестируемость

**Поле ввода.** Дефолтное действие тапа — открыть поле ввода с кнопкой
«Отправить». Отправка вызывает распознаватель с тем же `elementId` и тем
же текстом, что дала бы речь. Это основная поверхность автотестов: агент
проходит полный путь пользователя без синтеза речи.

**Прямой хук.** Дополнительно открывается точка вызова в обход касаний,
задокументированная комментарием рядом с кодом. Хук обязан повторять
контракт §5 ровно, без собственной валидации и без отдельных веток.

**Воспроизводимость.** Действующие значения констант §3 и параметров Θ
пишутся в журнал при каждом показе оверлея. Любая запись должна быть
воспроизводима без знания того, какая конфигурация стояла в тот день.

## 11. Что запрещено

- Создавать слушатели событий на элементах вне единого модуля приёма.
- Ветвить интерпретацию ввода по типу элемента внутри слоя приёма.
- Переопределять действие тапа где-либо, кроме единой таблицы (§2).
- Оставлять доступные пользователю элементы без `agent-action-id`.
- Исполнять команду на промежуточном транскрипте.
- Переставлять кандидатов после заморозки (§4).
- Исполнять команду с незаполненным обязательным слотом (§7).
- Исполнять команду, чьи идентификаторы отсутствуют в снимке (§2).
- Заканчивать отказ молча, без сообщения и записи в журнал (§2).
- Дублировать в этом документе параметры Θ и формы команд.
- Править `resolver.js` под форму данных хоста — адаптируется вход (§2).
- Называть команду отображения именем без префикса `show` (§6).
