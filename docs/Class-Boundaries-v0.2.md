# Описание границ классов

Статус: обязательный контракт между модулями VoiceList v0.2.
База разработки: main, исходный SHA 413e94056429af08565b14484a7f708fe8ee3906.
Изменения контракта согласовываются до изменения вызывающих модулей.
Способ внутреннего хранения не является частью этого документа.

## Классы и направление зависимостей

Client → DocumentRuntime (один ListDocumentDO)
DocumentRuntime содержит InteractionJournal, AgentHarness, ActionService, TaskGraph, Presentation.
AgentHarness запускает TaskAgent. Это обычные классы внутри одного DO, не дополнительные DO.

| Класс | Мета-методы | Граница ответственности |
| --- | --- | --- |
| Client | connect(), render(document), handleInput(input), submit(input), resume(cursor), disconnect() | Рендер дерева, локальные жесты/ASR, отправка ввода, доставка и повторы |
| DocumentRuntime | submit(input), getDocument(viewContext), follow(cursor), processPending() | Публичная граница, валидация, маршрутизация, согласованность и восстановление |
| InteractionJournal | appendInteraction(input), enrich(id, modelData), read(query), chain(id) | Append-only шина ввода, точного model context, raw response, parsed answer/commands, версий и `corrects`; без результатов исполнения |
| AgentHarness | buildContext(entry), invoke(modelContext), parse(raw), schedule(rule), cancelSchedule(id) | Только text-записи: точный контекст → model transport → детерминированный parser с тройкой версий |
| TaskAgent | buildContext(trigger), invoke(context), parse(raw) | Чистая подготовка/интерпретация модели. Без мутаций |
| ActionService | execute(entry, command, index) | Исполнение команды и изменение графа; status/error/undo/UI-effects пишутся только в private executor ledger |
| TaskGraph | read(query), apply(commands, expectedRevision) | Сохраняемая проекция задач; только проверенные команды API |
| Presentation | compose(graph, interactions, viewContext) | Чистая сборка дерева компонентов со стабильными ID |

TaskGraph.apply вызывается только ActionService. Presentation не пишет в журнал.
Граф, InteractionJournal и private executor ledger фиксируются атомарно. Исход мутации не становится записью InteractionJournal.
Журнал команд не означает полную возможность восстановить граф: снимок графа необходим.

## Взаимодействие

1. Client отправляет готовую реплику с контекстом.
2. Runtime проверяет и сохраняет реплику; возвращает подтверждение приёма, не исполнения.
3. Для text-записи Harness сохраняет точный model context, вызывает model transport вне storage transaction и сохраняет raw response.
4. Детерминированный parser сохраняет answer/commands и версии contextBuilder/prompt/parser в той же записи.
5. UI-команда минует Harness; ActionService выполняет UI- или model-команду из записи шины.
6. Idempotency/status/error/undo/UI-effects по стабильному key `entryId:index` сохраняются в private executor ledger, а не в InteractionJournal.
7. Runtime вызывает Presentation и доставляет дерево клиенту.
8. Client.render отображает дерево. Локальная отрисовка не создаёт запись журнала.
9. Расписание создаёт триггер журнала и проходит тот же цикл.

Команды явных кнопок, перетаскивания и Realtime проходят тот же журнал и исполнитель без обязательного LLM-вызова.
Одна операция клиента создаёт одну interaction-запись. Ответ модели дополняет её и не запускает Harness повторно.

## Контракт внешних сообщений (не схема хранения)

submit принимает key={clientKey,seq}, context={elementId,view,revision,actionId?} и ровно одно:
text (завершённый текст пользователя) либо command (существующий API-конверт command/actId/actType/payload).
Повтор с тем же key и содержимым возвращает исходный приём/результат; другое содержимое с тем же key — REQUEST_KEY_REUSED.
Пустой/отменённый локальный ввод не отправляется. Сервер проверяет ID, тип элемента и допустимость команды.
Клиент не может объявить себя агентом/исполнителем и записать выдуманный результат.

receipt содержит requestId, cursor, status=accepted|completed|rejected, error при отказе.
getDocument принимает view=list|frontier|search|action|edit|settings|dialogues и параметры выбранного представления.
Документ: schemaVersion=1, revision (граф), cursor (журнал), view, root.
У каждого компонента: type, стабильный id, props, children.
Компонент несёт разрешённые действия, а не исполняемый JS/HTML от модели.
Контекст ID элемента не тождественен ID задачи; сервер разрешает связь. Удалённые/устаревшие цели не переадресуются молча.
follow(cursor) возвращает ограниченное продолжение разрешённых событий с nextCursor; при невозможности продолжения клиент получает новый документ.
HTTP: POST /api/v2/input, GET /api/v2/document, GET /api/v2/updates.
WebSocket /ws сохраняет существующие hello/command/utterance/ack/state адаптеры для совместимости.
Все входы вызывают Runtime и журнал, а не обходят ActionService.
Внешний клиент не получает секреты и служебный prompt. Сохранённый model context передаётся только странице соответствующего действия, потому что пользователь явно просматривает этот контекст.

## Представление и действия UI

Presentation — серверный класс. Client — браузерный класс.
Presentation получает граф, видимую часть журнала и контекст экрана, отдаёт дерево компонентов.
Компоненты списка, frontier, редактора, журнала и диалога сохраняют действующий визуальный язык приложения.
Минимальная лексика: application, toolbar, task-list, task, action-list, action, action-page, task-editor, settings, dialogues, text.
В props допустимы только данные и описания разрешённых действий. DOM создаёт Client из доверенных реализаций компонентов.
Задачи имеют стабильные ID; служебные элементы — собственные стабильные ID.
Изменение интерфейса — команда API с адресатом пользовательской сессии, не глобальное переключение всех клиентов.
Публичный actionId равен ID корневой text-записи. Общий журнал скрывает root UI-команды, коррекции и rollback; action-page показывает всю транзитивную `corrects`-цепочку.
Close/скролл/подсветка/черновик ASR — локальные состояния клиента.
Сама UI-команда хранится в шине; её исход и факт доставки UI-effect — только в executor ledger.

## Надёжность

- Повторная доставка и повтор запуска не повторяют выполненную мутацию.
- Завершённые ошибки не остаются в бесконечной клиентской очереди повторов.
- После await модели проверяется актуальность графа и выбранного контекста.
- Сбой записи не меняет опубликованную память/проекцию.
- Возобновление после перезапуска читает незавершённые события журнала.
- Queue/schedule Cloudflare Agents SDK — механизм исполнения, не замена журнала.
- Цепочка отката отменяет выбранное действие и все корректировки, не затирая независимые изменения; конфликт возвращается явно.
- Существующий API задач, MCP, Realtime и одноразовая серверная настройка ключа сохраняются.
- Изоляция Dev обязательна; Production не изменяется.

## Контракт Dev-деплоя

Этот раздел заменяет docs/DEPLOYMENT.md для данной ветки.
Целевой домен подтверждён пользователем: https://vlist-v02-dev.smileme.ai/.
Только новый Worker vlist-v02-dev с собственным namespace LIST_DOCUMENT; привязка к Production запрещена.
Допустимый источник: чистый коммит ветки codex/voice-interface-v0.2 с прошедшими проверками.
Команда: npm run build:v2 && npx wrangler deploy --config wrangler.dev.jsonc.
Ни основной wrangler.jsonc с Production-маршрутом, ни Production secrets не используются для деплоя.
Проверки: /health=200; schemaVersion=1 на /api/v2/document; открыть страницу, создать/изменить тестовую задачу, проверить журнал, коррекцию/откат и сохранение после перезагрузки.
Записать SHA, URL, Worker version/deployment ID и результаты перед завершением.
Откат: npx wrangler rollback <previous-dev-version-id> --config wrangler.dev.jsonc; возврат кода не является откатом данных.
При первом релизе предыдущей версии нет: выключить доступ к Dev при серьёзном сбое, сохранив данные; Production не трогать.
До публикации проверять свободен ли домен и права аккаунта.
Пользователь разрешил однократный перенос существующего OpenAI-ключа из Production в Dev. Для этого допускается временный служебный Worker без HTTP-маршрута: read-only RPC getOpenAIApiKey у Production и однократный configureOpenAIApiKey у Dev. После переноса служебный Worker удаляется. Секрет не выводится и не сохраняется локально; постоянной привязки Dev к Production нет. Задачи и настройки Production не меняются.
Перенос: после первого Dev-деплоя проверить /api/realtime/key/status; при configured=false выполнить npx wrangler deploy --config scripts/migrations/wrangler.key-transfer.jsonc (только до EXPIRES_AT). Cron раз в минуту переносит только ключ. После configured=true удалить временный Worker: npx wrangler delete --config scripts/migrations/wrangler.key-transfer.jsonc --force. Файлы миграции не содержат секретов; повторный запуск после истечения срока ничего не делает.
Первичный Dev: ключ перенесён без вывода значения, /api/realtime/key/status вернул configured=true, временный Worker переноса удалён.
