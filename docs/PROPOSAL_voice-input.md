# Задача: голосовое управление списком

Голос добавляется поверх существующего списка отдельным модулем, который
формирует команду и передаёт её на исполнение существующему исполнителю.

Стандарт поведения — `docs/INPUT_HANDLING_STANDARD.md`. Алгоритм
сопоставления цели — `docs/TASK_RESOLVER.md` + `src/resolver.js`. Этот
документ — привязка стандарта к репозиторию: адаптеры, имена полей,
порядок работ. **При расхождении побеждает стандарт.**

---

## 1. Что есть сейчас

- Список и управление им — работающий модуль (`list-manager.html`, `src/`).
- `src/list-interpreter.js` — **исполнитель**: `execute(state, input)`
  принимает `{command, actId, payload}`, возвращает `{patch,
  actionLogEntry}`, а для команд отображения — `viewMode`/`effect`.
  Разбора текста в нём нет.
- `src/resolver.js` + `src/test_resolver.js` — резолвер цели,
  `node src/test_resolver.js`, 10/10 PASS.
- Интерактивные элементы размечены `agent-action-id`.
- Голосового ввода нет.

## 2. Что добавляется

```
жест + речь  →  ПРИЁМ ВВОДА  →  РАСПОЗНАВАТЕЛЬ  →  ИСПОЛНИТЕЛЬ  →  патч
                   новое           новое          существующий
```

| Имя | Что делает | Где |
|---|---|---|
| `resolveCommands(text, context, snapshot)` | текст → кандидаты-команды | новый модуль |
| `resolver.resolve(text, rows)` | текст → `One \| Vector \| Empty` | `src/resolver.js` |
| `execute(state, command)` | команда → патч | `src/list-interpreter.js` |

Взаимодействие коротко: долгое удержание в любой точке экрана открывает
полноэкранный оверлей с живой транскрипцией; вверх от пальца — кандидаты,
точка пальца — «как есть», ниже — отмена; свайп влево по элементу
открывает тот же оверлей с прицепленным контекстом. Пороги, формула выбора
строки и краевые случаи — в стандарте §3–§4.

## 3. Адаптер снимка — обязателен

`resolver.js` не переписывается под форму данных этого репозитория. Вход
приводится адаптером.

| В репозитории | В резолвере | Преобразование |
|---|---|---|
| `id` | `id` | без изменений |
| `line1` | `title` | `title = line1` |
| `status` | `status` | `Done → closed`, `Archive → superseded`, `Open`/`Focus`/`Pause` → `open` |
| `parentId`, `order`, `line2`, `collapsed`, `tags` | — | не передаются |

Без адаптера фильтр резолвера не сработает никогда: он отбрасывает
`closed` и `superseded` строчными, а в репозитории статусы с заглавной —
и завершённые задачи попадут в кандидаты.

Смысл отображения: `Done` — выполнено, `Archive` — снято с работы, целями
команд быть не должны. `Focus` и `Pause` — рабочие состояния (они же
нативные статусы бэкенда), задача остаётся доступной.

## 4. Что добавляется в исполнитель

| Команда | Класс | Что делает |
|---|---|---|
| `setParent` | изменение | `actId` — переносимый элемент, `payload.parentId` — новый родитель. Порядок пересчитать через существующий `nextOrder` |
| `showSearch` | отображение | `payload.query` — запрос; возвращает `viewMode: 'search'` и найденное множество в `effect` |

Два условия, которые нельзя нарушить:

1. **Имя `showSearch`, а не `search`.** Исполнитель опознаёт команды
   отображения по префиксу `show` и по этому же признаку не пишет их в
   журнал: `!String(input.command).startsWith('show') && input.command !==
   'viewItem'`. Команда `search` попала бы в журнал действий.
2. **`setParent` отвергает циклы** — перенос в самого себя или в
   собственного потомка, без патча и без записи журнала. Обход поддерева
   уже реализован: функция `descendants(items, rootId)` в том же файле.
   Распознаватель дополнительно не показывает такие цели в стеке.

## 5. Inbox

Служебный элемент верхнего уровня с фиксированным идентификатором `inbox`.
Всё, сказанное без контекста, попадает туда: «добавь …» без контекста →
`addChild` с `actId = 'inbox'`.

- Создаётся при инициализации списка, если отсутствует.
- Защищён: `deleteItem`, `setParent` и `editItem` с `actId = 'inbox'`
  отвергаются исполнителем без патча и без записи журнала.
- Отображается в списке как обычный элемент, дети переносятся из него
  обычными командами.

## 7. Этапы

1. Inbox и его защита (§5).
2. `setParent` и `showSearch` в исполнителе, с тестами (§4).
3. Адаптер снимка (§3), с тестом на то, что `Done` и `Archive` не
   попадают в кандидаты.
4. Слой приёма ввода: жесты, пороги, оверлей без распознавания —
   проверяется на заглушке кандидатов.
5. `resolveCommands`: словарь без контекста и с контекстом, ранжирование,
   заморозка порядка, вызов `resolver.resolve` для команд с целью.
6. Фолбэк на модель, тост, поведение при недоступном канале.

Этапы 1–3 не зависят от 4–6 и могут идти параллельно.

## 8. Приёмка

- Прокрутка списка не ломается ни одним из новых жестов.
- Строка под пальцем не подменяется после начала выбора.
- Команда не исполняется на промежуточном транскрипте.
- Команда с незаполненным обязательным слотом не исполняется частично.
- `setParent` не создаёт циклов; inbox не удаляется и не переносится.
- Команды отображения не создают записей журнала; `showSearch` в журнал не
  попадает.
- Задачи в статусах `Done` и `Archive` не появляются среди кандидатов.
- Команда с идентификатором, которого нет в снимке, отвергается с тостом.
- При недоступном фолбэк-канале речь не теряется, результат отменяется
  одним `undo`.
- Весь путь пользователя проходится автотестом через поле ввода, без
  синтеза речи.
- `node src/test_resolver.js` проходит в CI.
