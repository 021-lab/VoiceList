# Интеграция GPT-Live (Responses delegation)

Статус: целевая архитектура. Заменяет голосовой путь на базе OpenAI Realtime API
целиком — старая реализация удаляется, а не остаётся под флагом.

Единственное продуктовое требование этой итерации: логировать всю информацию,
которую отдаёт фреймворк OpenAI. Всё остальное подчинено ему.

## Почему переделка, а не доработка

В прежней схеме браузер обменивался аудио и событиями с OpenAI напрямую по
WebRTC, а Worker только пересылал SDP. Сервер не видел ни одного события, и
единственным журналом был localStorage браузера. Требование серверного лога
несовместимо с такой топологией, поэтому меняется именно она.

## Топология

```
браузер ──WebRTC: аудио + события──► gpt-live-1 ──delegation──► бэкенд-модель
   │                                    ▲   │
   │  POST /api/live/session            │   │
   └──────────────► Worker ─────────────┘   │
                      │                     │
              документ-DO ◄──sideband WS────┘
              (лог, мутации дерева, function_call_output)
```

Голос идёт напрямую между браузером и моделью. Документ-DO вторым соединением
(sideband) подключается к той же сессии: он получает те же самые JSON-события,
что и браузер, пишет их в лог, исполняет вызовы инструментов и возвращает
результаты в ту же сессию.

## Принятые решения

| Предмет | Решение |
| --- | --- |
| Голосовая модель | `gpt-live-1` |
| Режим делегирования | `responses` |
| Бэкенд-модель | Переменная конфига, дефолт `gpt-5.6-luna` |
| Аудио | Браузер ↔ модель напрямую, WebRTC |
| Управляющий канал | Sideband WebSocket из существующего документ-DO |
| Исполнение инструментов | DO мутирует дерево и отвечает `function_call_output` |
| Дерево для голоса | Снимок в `session.instructions` |
| Дерево для бэкенда | Только затронутые узлы в тексте делегирования |
| Состав снимка | Статусы Open, Focus, Pause, Info; без Done и Archive |
| Актуальность снимка | Дельты через `session.instructions.append` |
| Разрешение названия | Голос уточняет у пользователя и делегирует готовый id |
| Глубина лога | Финальные объекты, без промежуточных дельт |
| Форма лога | Плоский поток событий |
| Хранилище лога | SQLite документ-DO, отдельная таблица |
| Доступ к логу | HTTP-ручка, экрана в интерфейсе нет |
| `store` у OpenAI | Включён |

## Разделение промптов

Два слоя получают разные инструкции, и это не стилистическое деление.

`session.instructions` — голосовой слой. Роль, манера речи, язык, правила
уточнения и, главное, условия обращения к бэкенду. Здесь же лежит снимок
дерева: без него голос не сможет разрешить произнесённое название в id, не
обращаясь к бэкенду. Документация прямо отводит этому полю роль «когда просить
помощи у бэкенда».

`delegation.responses.instructions` — бэкенд-модель. Процедуры работы с
задачами, правила выбора инструмента, обработка отказов.

Голосовому слою разрешено обрабатывать самому: короткое уточнение, приветствие,
повтор уже названного результата, ответ из текущего контекста. Запрещено —
отвечать по существу, не дождавшись бэкенда, когда ответ от бэкенда зависит.

### Уточнение названия задачи

Голос разрешает произнесённое название по снимку. При нескольких совпадениях
или низкой уверенности он переспрашивает и ждёт подтверждения пользователя, не
делегируя. Делегирование происходит только после подтверждения, и в него уходит
уже конкретный id.

Это UX-уровень, а не гарантия целостности. Гарантией остаётся проверка id в DO:
несуществующий или неподходящий id отвергается, причина уходит в модель.

## Границы записей лога

Фреймворк сам задаёт единицу работы, и лог опирается на неё, а не на эвристику.

- `session.delegation.created` несёт `delegation.id`, `delegation.target` и
  `offset_ms` — момент, когда голос решил звать бэкенд.
- События бэкенда приходят обёрнутыми в `response.event` с внешним
  `delegation_id`; внутри — `response.created`, `response.output_item.done`
  (вызов инструмента с `call_id`, `name`, `arguments`), `response.completed`.
- Транскрипт-дельты несут `start_ms` и `end_ms`, поэтому речь привязывается к
  делегированию по таймлинии, а не по догадке о границе реплики.

Обмены, в которых голос уточнял название и не делегировал, своего
`delegation_id` не имеют. Лог пишется плоским потоком с таймстемпами, и такие
обмены просто не получают привязки; группировка делается при чтении.

## Схема лога

Таблица `live_events` в SQLite документ-DO, по строке на событие:

| Поле | Содержание |
| --- | --- |
| `seq` | Монотонный номер в рамках сессии |
| `live_session_id` | Идентификатор сессии GPT-Live |
| `at` | Время записи на сервере |
| `offset_ms` | Позиция на таймлинии сессии, если событие её несёт |
| `type` | Тип события фреймворка |
| `delegation_id` | Привязка к делегированию, если есть |
| `response_id` | Идентификатор ответа бэкенд-модели, если есть |
| `call_id` | Идентификатор вызова инструмента, если есть |
| `direction` | `in` от фреймворка, `out` от нас |
| `payload` | Событие целиком, как пришло |

Пишутся финальные объекты: старт и закрытие сессии, usage, создание
делегирования, `response.created` и `response.completed`, завершённые
`output_item`, ошибки, подтверждения наших append-операций, а также всё, что мы
отправляем сами — `response.item.create`, `response.create`,
`session.instructions.append`. Промежуточные дельты не пишутся, транскрипты
сохраняются как поток с таймстемпами.

Полнота проверяется контрактным тестом: перечень типов событий, которые обязаны
дойти до таблицы, фиксируется в тесте и ломается при расхождении.

## Инструменты

Набор изменений дерева задач не меняется по составу: создание корневой задачи и
дочерней, добавление информации, смена статуса, дедлайн, переименование,
перемещение, чтение фронтира. Изменилось место объявления: теперь они живут в
`delegation.responses.tools`, а не в конфигурации сессии.

Бэкенд-модель только выбирает инструмент и аргументы. Исполняет DO, он же
возвращает `function_call_output` на каждый ожидающий вызов и затем
`response.create`, чтобы бэкенд продолжил работу.

## Жизненный цикл и устойчивость

Сессия создаётся строго по нажатию кнопки. Предварительный прогрев недопустим:
создание WebRTC-сессии тарифицируется как пятнадцать секунд разговора.

Документ-DO должен оставаться живым весь разговор. Аудио через него не идёт, а
sideband — исходящее соединение, поэтому механизм гибернации на нём не работает.
Якорем служит WebSocket синхронизации списка, который браузер и так держит
открытым во время звонка.

Ключ OpenAI остаётся на сервере. Клиентский секрет не нужен: SDP-обмен выполняет
наш Worker.

## Стоимость

Голосовой слой — пять центов за минуту, посекундно. Бэкенд-модель и инструменты
тарифицируются отдельно. Снимок дерева участвует в каждом ходу голосового слоя,
поэтому его размер — параметр стоимости, а не деталь оформления; исключение
завершённых и архивных задач принято в том числе поэтому.

## Открытые вопросы

- Рост `session.instructions` от дельт. Каждый append ограничен пятьюстами
  токенами, но инструкции растут монотонно, а документированного способа их
  схлопнуть нет. Решено отложить: счётчик дельт и размер инструкций пишутся в
  лог, порог компактизации выбирается по реальным данным.
- Поведение при обрыве sideband посреди делегирования.
- Изоляция сессий и лога по пользователям на общем документ-DO.
- Срок жизни лога: автоудаления нет, чистка ручная.
