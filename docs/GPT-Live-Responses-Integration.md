# Интеграция GPT-Live (Responses delegation)

Статус: реализовано и развёрнуто на дев-окружении. Заменяет голосовой путь на базе OpenAI Realtime API
целиком — старая реализация удаляется, а не остаётся под флагом.

Единственное продуктовое требование этой итерации: логировать всю информацию,
которую отдаёт фреймворк OpenAI. Всё остальное подчинено ему.

## Почему переделка, а не доработка

В прежней схеме браузер обменивался аудио и событиями с OpenAI напрямую по
WebRTC, а Worker только пересылал SDP. Сервер не видел ни одного события, и
единственным журналом был localStorage браузера. Требование серверного лога
несовместимо с такой топологией, поэтому меняется именно она.

## Топология

```
браузер ──WebRTC: аудио + события──► gpt-live-1 ──delegation──► бэкенд-модель
   │                                    ▲   │
   │  POST /api/live/session            │   │
   └──────────────► Worker ─────────────┘   │
                      │                     │
              документ-DO ◄──sideband WS────┘
              (лог, мутации дерева, function_call_output)
```

Голос идёт напрямую между браузером и моделью. Документ-DO вторым соединением
(sideband) подключается к той же сессии: он получает те же самые JSON-события,
что и браузер, пишет их в лог, исполняет вызовы инструментов и возвращает
результаты в ту же сессию.

## Принятые решения

| Предмет | Решение |
| --- | --- |
| Голосовая модель | `gpt-live-1` |
| Режим делегирования | `responses` |
| Бэкенд-модель | Настройка приложения; конфиг задаёт умолчание |
| Аудио | Браузер ↔ модель напрямую, WebRTC |
| Управляющий канал | Sideband WebSocket из существующего документ-DO |
| Исполнение инструментов | DO мутирует дерево и отвечает `function_call_output` |
| Дерево для голоса | Снимок в `session.instructions` |
| Дерево для бэкенда | Только затронутые узлы в тексте делегирования |
| Состав снимка | Статусы Open, Focus, Pause, Info; без Done и Archive |
| Формат снимка | Плоская таблица с шапкой, не JSON |
| Идентификаторы задач | base36 от счётчика с 1000; прежние не трогаем |
| Промпты | Оба редактируются в настройках и моделью по просьбе |
| Правка промпта моделью | Дописать правило или заменить текст целиком |
| Откат промптов | История версий в Durable Object |
| Порядок работ | Смена идентификаторов входит в работу над голосом |
| Актуальность снимка | Дельты через `session.instructions.append` |
| Разрешение названия | Голос уточняет у пользователя и делегирует готовый id |
| Глубина лога | Финальные объекты, без промежуточных дельт |
| Форма лога | Плоский поток событий |
| Хранилище лога | SQLite документ-DO, отдельная таблица |
| Доступ к логу | HTTP-ручка без токена, экрана в интерфейсе нет |
| Чистка лога | Не чистим, наблюдаем за размером |
| Изоляция | Не нужна: один пользователь на документ-DO |
| `store` у OpenAI | Запрошен и подтверждён фактическим конфигом сессии |

## Разделение промптов

Два слоя получают разные инструкции, и это не стилистическое деление.

`session.instructions` — голосовой слой. Роль, манера речи, язык, правила
уточнения и, главное, условия обращения к бэкенду. Здесь же лежит снимок
дерева: без него голос не сможет разрешить произнесённое название в id, не
обращаясь к бэкенду. Документация прямо отводит этому полю роль «когда просить
помощи у бэкенда».

`delegation.responses.instructions` — бэкенд-модель. Процедуры работы с
задачами, правила выбора инструмента, обработка отказов.

Голосовому слою разрешено обрабатывать самому: короткое уточнение, приветствие,
повтор уже названного результата, ответ из текущего контекста. Запрещено —
отвечать по существу, не дождавшись бэкенда, когда ответ от бэкенда зависит.

### Формат снимка

Снимок передаётся плоской таблицей с шапкой, по строке на задачу: собственный
идентификатор, идентификатор родителя, статус, название. Разделитель —
табуляция.

```
id	parent	st	title
rs	-	O	Яблоки
rt	rs	O	Голден
ru	rs	P	Фуджи
rv	ru	F	Первый позад
rw	-	O	Кофе
```

Плоская форма выбрана вместо отступов по двум причинам. Инструменты принимают
`parentId` прямым аргументом, и строка подаёт ровно то значение, которое уйдёт в
вызов, — не требуется выводить родителя из визуальной позиции. А дерево здесь
глубокое, до пяти уровней, и отступ на такой глубине различается ненадёжно:
ведущие пробелы склеиваются токенизатором.

Собственный идентификатор стоит первым: строка читается как запись о задаче, что
совпадает с тем, как её использует модель — нашла задачу по названию, взяла
идентификатор из начала строки. Шапка снимает двусмысленность между двумя
похожими идентификаторами в строке и стоит один раз на снимок. Строки
упорядочены обходом дерева сверху вниз, поэтому плоский список сохраняет и
связность, и порядок соседних задач, не опираясь при этом ни на один пробел.

Статусы обозначаются буквой: `O` открыта, `F` фокус, `P` пауза, `I` информация.
Done и Archive в снимок не входят. Корень отмечается прочерком в колонке
родителя.

Дельты пишутся в том же языке, по строке на изменение: `+ rx rs O Гренни Смит`
создание, `~ ru Фуджи красные` переименование, `* ru F` смена статуса,
`> ru rw` перемещение, `^ ru 09-20` дедлайн, `- ru` уход в Done или Archive.

### Идентификаторы задач

Генерация переводится на base36 от счётчика, начиная с 1000, — так же, как это
сделано в v1-ядре: `encodeId = value => Number(value).toString(36)`, первый
выданный идентификатор `rs`. Развёрнутая система выдаёт `crypto.randomUUID()`,
тридцать шесть символов и около пятнадцати токенов; в плоской таблице строка
несёт два идентификатора, так что на списке в двести задач это тысячи токенов в
каждом ходу голосового слоя. Сверх стоимости модель обязана воспроизводить
идентификатор посимвольно в аргументе инструмента, а UUID для этого худший из
форматов.

Ранее выданные идентификаторы остаются как есть. Сессионные алиасы не вводятся:
короткие идентификаторы делают их лишними.

Счётчик хранится, а не вычисляется из максимума существующих идентификаторов.
Причина в том, что вычисляемый максимум переиспользует идентификатор удалённой
задачи, а журнал взаимодействий ссылается на прежние идентификаторы, и такая
ссылка начала бы указывать на другую задачу. Хранилище для счётчика уже есть:
таблица `vl_meta` хранит целые значения по ключу, там же лежит `revision`.

Счётчик засевается числом 1000, а не максимумом существующих значений. Наследные
пятисимвольные идентификаторы из `randomId` используют тот же алфавит `[a-z0-9]`
и разбираются как корректные числа base36, поэтому засев по максимуму увёл бы
счётчик в произвольно большое значение. Вместо этого выданный кандидат
проверяется на занятость и при совпадении пропускается — так же, как в v1.
Идентификатор `inbox` зарезервирован.

Следствие, которое надо принять: пока в списке живут ранее созданные задачи,
снимок остаётся смешанным — новые задачи в нём короткие, старые по-прежнему
UUID. Стоимость снимка снижается по мере появления новых задач, а не сразу.

### Уточнение названия задачи

Голос разрешает произнесённое название по снимку. При нескольких совпадениях
или низкой уверенности он переспрашивает и ждёт подтверждения пользователя, не
делегируя. Делегирование происходит только после подтверждения, и в него уходит
уже конкретный id.

Это UX-уровень, а не гарантия целостности. Гарантией остаётся проверка id в DO:
несуществующий или неподходящий id отвергается, причина уходит в модель.

## Настройки приложения

Редактируются три значения: промпт голосового слоя, промпт бэкенд-модели и сама
бэкенд-модель. Хранятся там же, где сейчас живёт системный промпт голосового
агента, — в Durable Object; переменные конфига задают лишь умолчания.

Умолчания остаются в коде, а пустое сохранённое значение означает «взять
умолчание». Альтернатива — класть копию встроенного текста в хранилище при первом
открытии настроек — ломается дважды. Улучшенное умолчание перестаёт доезжать до
того, кто однажды сохранил свою редакцию: приложение читает его копию, снятую со
старой версии кода, и это выглядит как поглупевшая модель. И возврат к умолчанию
становится невозможен, потому что хранимую копию не отличить от осознанно
написанного текста, а эталона в хранилище нет. При правке промптов моделью это
перестаёт быть теорией: возврат к умолчанию — последняя линия отката.

Снимок дерева редактированию не подлежит. Пользователь правит только текст
инструкции, а блок с задачами приписывается системой при создании сессии. Иначе
редактор может удалить снимок и лишить голосовой слой возможности разрешать
названия, причём отказ будет выглядеть как деградация модели, а не как следствие
правки.

Бэкенд-модель вводится текстом и проверяется на непустоту и допустимый вид.
Список известных моделей быстро устаревает, а здесь один пользователь, который
знает, что вводит. Цена решения в том, что опечатка обнаружится не при
сохранении, а при первой сессии; она попадёт в лог отказом от API, и по логу
диагностируется однозначно.

Изменения вступают в силу со следующей сессии: конфигурация задаётся при её
создании. Экран настроек говорит об этом прямо, иначе правка во время разговора
выглядит как молчаливо проигнорированная.

Запись о старте сессии в логе несёт версии обоих промптов и имя бэкенд-модели.
Без этого запись за прошлую неделю нельзя прочитать: неизвестно, каким текстом
тогда управлялась модель.

## Правка промптов моделью

Пользователь может попросить голосом изменить промпт — свой или бэкенда. Это
даёт ещё четыре инструмента: чтение и запись для каждого из двух промптов.
Чтение нужно потому, что бэкенд-модель не видит инструкций голосового слоя и без
них не может править осмысленно.

Запись работает в двух режимах: дописать одно правило в конец либо заменить текст
целиком. Первый режим ничего не теряет и годится для «отвечай короче»; второй
нужен, когда правило надо убрать или переформулировать, и требует
предварительного чтения.

Правка применяется немедленно и сохраняется на будущее. Промпты задаются при
создании сессии, поэтому иначе получалась бы ловушка: пользователь просит
изменить поведение, модель послушно правит текст, а в текущем разговоре ничего
не меняется. Немедленное применение делается штатными средствами —
`session.instructions.append` для голосового слоя и `session.update` для полей
`delegation.responses`.

### Ограничения

Названия задач объявлены недоверенными данными и лежат в снимке. Инструмент
записи в промпт повышает цену внедрения: подсунутая правка переживёт сессию,
тогда как обычное внедрение действует только в пределах разговора. Поэтому:

- правка промпта требует явного подтверждения голосом, как и разрешение названия
  задачи, и никогда не выполняется как побочное следствие другой просьбы;
- прежний и новый текст целиком попадают в лог;
- Durable Object хранит историю версий каждого промпта, и вернуть можно любую;
- возврат к встроенному умолчанию доступен всегда — это очистка поля.

История версий и составляет откат. Возврат к умолчанию остаётся отдельной
операцией: он нужен, когда испорчены все сохранённые версии.

## Границы записей лога

Фреймворк сам задаёт единицу работы, и лог опирается на неё, а не на эвристику.

- `session.delegation.created` несёт `delegation.id`, `delegation.target` и
  `offset_ms` — момент, когда голос решил звать бэкенд.
- События бэкенда приходят обёрнутыми в `response.event` с внешним
  `delegation_id`; внутри — `response.created`, `response.output_item.done`
  (вызов инструмента с `call_id`, `name`, `arguments`), `response.completed`.
- Транскрипт-дельты несут `start_ms` и `end_ms`, поэтому речь привязывается к
  делегированию по таймлинии, а не по догадке о границе реплики.

Обмены, в которых голос уточнял название и не делегировал, своего
`delegation_id` не имеют. Лог пишется плоским потоком с таймстемпами, и такие
обмены просто не получают привязки; группировка делается при чтении.

## Схема лога

Логической единицей является одно событие — не реплика, не ход разговора и не
делегирование. Это следует прямо из требования: фреймворк отдаёт поток событий,
и записать надо именно его. Если взять за единицу делегирование, то всё
происходящее вне делегирования — уточнения названия, приветствия, старт и
закрытие сессии, usage, ошибки — не получит места в схеме, и лог перестанет
быть полным по построению.

Поэтому делегирование, реплика и вызов инструмента — это группировки при
чтении, а не отдельные таблицы. Колонки `delegation_id`, `response_id` и
`call_id` не задают структуру, а позволяют восстановить её запросом.

Таблица `live_events` в SQLite документ-DO, по строке на событие:

| Поле | Содержание |
| --- | --- |
| `seq` | Монотонный номер в рамках сессии |
| `live_session_id` | Идентификатор сессии GPT-Live |
| `at` | Время записи на сервере |
| `offset_ms` | Позиция на таймлинии сессии, если событие её несёт |
| `type` | Тип события фреймворка |
| `delegation_id` | Привязка к делегированию, если есть |
| `response_id` | Идентификатор ответа бэкенд-модели, если есть |
| `call_id` | Идентификатор вызова инструмента, если есть |
| `direction` | `in` от фреймворка, `out` от нас |
| `payload` | Событие целиком, как пришло |

Пишутся финальные объекты: старт и закрытие сессии, usage, создание
делегирования, `response.created` и `response.completed`, завершённые
`output_item`, ошибки, подтверждения наших append-операций, а также всё, что мы
отправляем сами — `response.item.create`, `response.create`,
`session.instructions.append`. Промежуточные дельты не пишутся, транскрипты
сохраняются как поток с таймстемпами.

Полнота проверяется контрактным тестом: перечень типов событий, которые обязаны
дойти до таблицы, фиксируется в тесте и ломается при расхождении.

### Пример потока

Запрос «поставь первый в фокус», в котором голос сначала уточнил, какая из двух
похожих задач имеется в виду:

| seq | type | deleg | call | напр. | содержание |
| --- | --- | --- | --- | --- | --- |
| 1 | `session.started` | | | in | |
| 2 | `session.input_transcript` | | | in | «поставь первый в фокус» |
| 3 | `session.output_transcript` | | | in | «Первый поход или Первый позад?» |
| 4 | `session.input_transcript` | | | in | «первый позад» |
| 5 | `session.delegation.created` | d1 | | in | `offset_ms=8120` |
| 6 | `response.created` | d1 | | in | `resp_7` |
| 7 | `response.output_item.done` | d1 | c1 | in | `setStatus{first, Focus}` |
| 8 | `response.item.create` | d1 | c1 | out | `function_call_output {ok}` |
| 9 | `response.create` | d1 | | out | |
| 10 | `response.completed` | d1 | | in | |
| 11 | `session.output_transcript` | | | in | «Готово» |
| 12 | `session.instructions.append` | | | out | `* first F` |
| 13 | `session.instructions.appended` | | | in | подтверждение |
| 14 | `session.usage.updated` | | | in | |

Строки со второй по четвёртую — уточнение без делегирования: `delegation_id` у
них пуст, и при чтении они относятся к окну до `offset_ms` пятой строки. Строки
8, 9 и 12 отправлены нами; они лежат в той же таблице, иначе по логу не
восстановить, что именно было возвращено модели.

## Инструменты

Набор изменений дерева задач не меняется по составу: создание корневой задачи и
дочерней, добавление информации, смена статуса, дедлайн, переименование,
перемещение, чтение фронтира. Изменилось место объявления: теперь они живут в
`delegation.responses.tools`, а не в конфигурации сессии.

Бэкенд-модель только выбирает инструмент и аргументы. Исполняет DO, он же
возвращает `function_call_output` на каждый ожидающий вызов и затем
`response.create`, чтобы бэкенд продолжил работу.

## Жизненный цикл и устойчивость

Сессия создаётся строго по нажатию кнопки. Предварительный прогрев недопустим:
создание WebRTC-сессии тарифицируется как пятнадцать секунд разговора.

История между сессиями не сквозная: новая сессия стартует с пустым `input`.
Перенести часть прошлого разговора можно явно — `input` принимает до 128
сообщений и 8 192 токенов суммарно, а собрать его есть из чего, транскрипты
лежат в логе.

Отсюда же следует механизм схлопывания инструкций. Приросты
`session.instructions.append` живут только до конца сессии, поэтому пересоздание
сессии и есть схлопывание: новая сессия получает свежий полный снимок и ноль
дельт. Форк для этого не годится — он наследует исходные инструкции, то есть
устаревший снимок дерева, и воспроизводит прошлое состояние вместо обновления.
`store` даёт лишь тридцатидневную запись как подстраховку при разборе
инцидентов; форк как механизм обновления он не спасает.

Документ-DO должен оставаться живым весь разговор. Аудио через него не идёт, а
sideband — исходящее соединение, поэтому механизм гибернации на нём не работает.
Якорем служит WebSocket синхронизации списка, который браузер и так держит
открытым во время звонка.

Ключ OpenAI остаётся на сервере. Клиентский секрет не нужен: SDP-обмен выполняет
наш Worker.

## Доступы и секреты

Состояние на момент проектирования, проверено против развёрнутого окружения.

Деплой доступен: `CLOUDFLARE_API_TOKEN` действует, аккаунт совпадает с
`account_id` в `wrangler.dev.jsonc`. Развёрнутый воркер — `vlist-v02-dev`,
отвечает на `/health`.

Ключ OpenAI настроен, но лежит не там, где ожидалось. Секретов у `vlist-v02-dev`
нет ни одного, `OPENAI_API_KEY` не задан ни секретом, ни переменной. Ключ хранится
внутри Durable Object и был задан однократно через `/api/realtime/key`:
`/api/realtime/key/status` отвечает `configured: true, setupAvailable: false`.

Повторно задать ключ через приложение нельзя. `configureOpenAIApiKey` отдаёт
отказ, если однократная установка уже израсходована, а она израсходована. Если
хранимый ключ не подойдёт для GPT-Live, заменить его получится только сбросом
документа или правкой кода.

Отсюда рекомендация: задать ключ секретом воркера. Все пути чтения устроены как
`env.OPENAI_API_KEY || await stub.getOpenAIApiKey()`, поэтому секрет имеет
приоритет над хранимым значением, ротируется свободно и не трогает состояние
документа.

Тариф проекта платный, это подтверждено владельцем. Есть ли у ключа доступ к
GPT-Live, отсюда не проверить: секреты Cloudflare доступны только на запись, и
значение ключа не читается ни через API, ни через wrangler. Выяснится первым
реальным запуском.

Настройка `store` отказывает молча: под Zero Data Retention поле трактуется как
`false` без ошибки, поэтому успешный ответ выглядит одинаково при включённом и
выключенном хранении. Проверять пришлось иначе — по фактическому конфигу сессии,
который приходит в событии `session.started` и пишется в лог целиком. Первая
реальная сессия на дев-окружении вернула `store: true`, то есть хранение для
проекта разрешено.

Полагаться на него всё равно не стоит: единственным гарантированным источником
остаётся лог в Durable Object. Но расхождение запрошенного и фактического
значения теперь видно в логе сразу, а не через тридцать дней по отсутствию
записи.

Ручка чтения лога намеренно открыта: это рабочая запись того, что вернул
фреймворк, и токен мешал её читать. Следствие принимается сознательно — лог
содержит расшифровки речи и названия задач, а домен публичный, поэтому прочитать
его может любой, кто знает адрес.

## Стоимость

Голосовой слой — пять центов за минуту, посекундно. Бэкенд-модель и инструменты
тарифицируются отдельно. Снимок дерева участвует в каждом ходу голосового слоя,
поэтому его размер — параметр стоимости, а не деталь оформления; исключение
завершённых и архивных задач принято в том числе поэтому.

## Что проверено на дев-окружении

Реализация развёрнута на `vlist-v02-dev` и проверена против настоящего API.

Идентификаторы: созданная через API задача получила `rs`, то есть счётчик base36
работает на живых данных.

Сессия: настоящее WebRTC-предложение из Chromium принято, `POST /v1/live/sessions`
вернул `201` с идентификатором сессии и SDP-ответом. Это подтверждает и доступ
ключа к GPT-Live, и то, что строгий конфиг сессии принят целиком — неизвестное
поле он отверг бы.

Sideband: соединение из Durable Object к `/attach` открылось, и событие
`session.started` от GPT-Live дошло до лога. Его payload вернул фактический
конфиг: `gpt-live-1`, голос `marin`, делегирование `responses` с моделью
`gpt-5.6-luna`, двенадцать инструментов и `store: true`.

Лог: читается ручкой. Отказы пишутся наравне с успехами — и отклонение от OpenAI
с его текстом, и обрыв, при котором запрос вообще не ушёл.

Настройки: правка промпта, смена модели, отклонение недопустимого имени модели,
возврат к встроенному умолчанию и история версий отработали на развёрнутом
стенде.

Чего проверить отсюда нельзя: ICE в этом контейнере не завершается, наружу открыт
только HTTPS. Поэтому звук не пошёл, транскриптов и вызовов инструментов на живой
сессии не было — эта часть проверяется только с настоящего устройства с
микрофоном. Проверка повторяется командой `npm run smoke:live`.

## Открытые вопросы

- Порог пересоздания сессии. Механизм схлопывания известен, не выбрано значение.
  Счётчик дельт и размер инструкций пишутся в лог, порог выбирается по реальным
  данным.
- Переживают ли приросты инструкций замену голосового движка. На 90% контекста
  Live поднимает заменяющий движок внутри той же сессии и передаёт ему исходные
  инструкции и до 8 192 токенов истории; приросты в эту формулу не входят.
  Прямого утверждения в документации нет. На выводы это не влияет: истина о
  дереве в DO, а проверка id при мутации ловит расхождение.
- Поведение при обрыве sideband посреди делегирования.
- Живой разговор целиком: звук, транскрипты и вызовы инструментов проверяются
  только с устройства с микрофоном.
- Рост таблицы лога. Автоудаления нет сознательно; за размером наблюдаем и
  возвращаемся к вопросу, когда он станет заметен.
